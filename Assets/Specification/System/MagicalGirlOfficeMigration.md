현행 명세를 미래 목표와 동시에 실행 규칙으로 취급하지 않는다. 각 단계에서 상세 규칙과 TODO를 먼저 확정하고 해당 범위의 TaskSystem 및 관련 데이터 명세를 갱신한 뒤 구현한다. 승인 전 목표 규칙을 기존 캠페인에 섞지 않는다.

## 2. 단계와 완료 조건

### M0 — 방향 기준 확립

- 청사진·이 계획·유지/변경/폐기 목록을 기록한다.
- 합의한 방향과 상세 설계 권고안/TODO를 구분한다.
- 결과: 미래 설계의 기준 문서. 현재 런타임 사양의 대체나 개발 완료 선언은 아님.
- 이번 문서화 작업의 범위는 M0다. M1 이후는 미착수다.

### M1 — 모니터 안의 7일 시나리오

- 기존 UI를 활용해 인물 3명, 출동 사건 1개, 학교 일정 충돌 1개, 휴식 요청 1개, 졸업 준비 안건 1개와 후속 메시지를 작성한다.
- 지도는 간단한 구역 목록·도식으로 시작한다. 직접 전투·현장 장면·상담 연출·전면 관계 시뮬레이션은 제외한다.
- 새 시나리오와 기존 캠페인의 구분 및 별도 저장 경계를 먼저 마련한다.
- 완료 기준: 현장 묘사 없이 선택 이유와 결과를 이해하고 인물의 사정을 기억할 수 있다.
- 보류 기준: 메시지 양만 늘고 선택의 의미가 전달되지 않으면 지도·장기 콘텐츠 확장 전에 정보와 사건을 수정한다.

### M2 — 안정화·보호·솔직한 관계

- 단기 안정과 장기 숙련, 수업 제약, 출동 제한·거절·철수, 사전 방침을 상세 명세화한다.
- 사실/발언/추정과 갱신 시각을 구분하고 신뢰에 따른 표현·지원 요청을 구현한다.
- 비전투 안정화와 회복 경로를 포함한다.
- 완료 기준: 수동·자동배정이 동일한 제약을 지키고, 높은 신뢰의 솔직한 보고가 악화로 오인되지 않는다.
- 필수 검증: 제한 인원 자동배정 방지, 거절 후 재배정 방지, 철수 후 기록·사건 상태, 긴급 안전 정보의 즉시 반영.

### M3 — 지역과 공공사업 경제

- 4개 지역, 이동·지원 시간, 기관 연계, 예방 효과를 추가한다.
- 기본 보조금·사례 지원·지역 계약·추가 임무의 산식과 평가 주기를 확정한다.
- 출동 횟수 외의 성과, 지원 요청과 계약 조정, 예산 부족 시 대응을 설계한다.
- 완료 기준: 과로 없이 운영 가능한 경로가 있고 예방 활동의 효과가 다음 일정에 드러난다.
- 필수 검증: 신고 은폐·대상자 기피·고위험 반복 출동이 보상상 지배적인 전략인지 비교한다. 숫자 밸런스는 실제 로그로 조정한다.

### M4 — 졸업과 멘토로 이어지는 마지막 한 달

- M1–M3을 확장해 졸업 예정자 1명이 포함된 4주 데모를 완성한다. 전체 성장기를 한 달로 압축하지 않는다.
- 개인 식별자와 슬롯을 분리하고 졸업 이력, 인계, 후임, 이후 소식을 저장한다.
- 관계·여유·의향·적합성을 반영한 멘토 제안과 참여/중단을 상세 설계한다.
- 경험에 기반한 훈련·대화 선택지를 구현한다. 멘토 미참여의 좋은 결말도 작성한다.
- 한 달 데모에서는 별도 후일담 시간 경과 또는 기존 졸업생을 통해 멘토 기능을 검증할 수 있다. 졸업 직후 자동 복귀를 일반 규칙으로 삼지 않는다.
- 완료 기준: 졸업이 손실만으로 읽히지 않고, 이전 인물의 기록이 후임에게 덮어써지지 않는다.
- 필수 검증: 저장/불러오기 후 이력·관계 유지, 멘토 일정과 보수·중단, 후배 정보의 자동 공유 방지.

### M5 — 외부 사용성과 장기 확장 판단

- 온보딩, 알림 우선순위, 읽기 부담, 사건 반복과 장기 운영을 검증한다.
- 질문: 인물과 걱정을 기억하는가, 배치 이유를 설명하는가, 결과가 납득되는가, 졸업을 성취로 느끼는가, 다음 이야기가 궁금한가.
- 안전한 운영의 경제성, 특정 멘토 조합의 고착, 기관 확대 시 관리 부담을 점검한다.
- 완료 기준: 설명 없는 플레이 관찰과 피드백을 근거로 장기 캠페인 확장 여부를 결정한다. 대중성이나 흥행을 검증 완료로 단정하지 않는다.

## 3. 데이터와 저장 전환

- 개인·사건·지역·기관·멘토 연결에 영구 ID를 사용한다. 표시 이름과 배열 위치를 식별자로 사용하지 않는다.
- 기존 세이브는 보존한다. 식민지 업무·재생 이력을 새 세계관으로 자동 변환하지 않는다.
- 새 캠페인은 별도 식별과 버전을 가진다. 지원하지 않는 버전은 조용히 덮어쓰지 않는다.
- UI 배치·사용자 설정은 호환되는 범위에서 유지한다.
- 졸업 후에도 과거 업무 소유자와 개인 이력은 원래 인물을 가리킨다. 후임에게는 새 ID를 부여한다.
- `DataAuthoring/ContentDataStructure.md`와 `DailyRuleSimulation.md`를 단계별로 갱신한다. JSON 필드·시간 처리·검증 규칙을 명세화하기 전 새 필드를 임의 추가하지 않는다.
- 관계·학교·멘토 콘텐츠는 소수의 수작업 사건으로 먼저 검증한다. 생성 콘텐츠 확대는 이후다.

## 5. 구현·배포 경계

재사용 여부는 실제 구현을 점검해 결정한다. 기존 창·일정·메일·데이터 구조가 있다는 사실을 새 기능이 이미 구현됐다는 뜻으로 해석하지 않는다.

현재 실행 가능한 버전을 Git 이력으로 보존하고 장기적인 이중 게임 모드 지원은 기본 범위에 넣지 않는다. 전환 중 필요한 최소한의 캠페인 분리만 수행한다.

각 단계는 명세 → 구현 → 해당 변경의 회귀 검증 → 배포 영향 판정 순서로 진행한다. AOT 경계·새 리소스·Contracts·저장 호환성을 실제 변경 기준으로 평가하며 패치만으로 가능하다고 선결정하지 않는다. 이 문서 커밋은 문서 전용이며 빌드·게시·디바이스 채널 변경을 포함하지 않는다.
