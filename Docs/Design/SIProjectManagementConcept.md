# ProjectW 현대 SI 프로젝트 관리 콘셉트 정리

## 문서 성격

- 이 문서는 대화에서 결정된 방향을 보존하기 위한 정리본이다.
- 아직 `Assets/Specification`에 반영된 공식 SSOT는 아니다.
- 구현 사양이 아니라 콘셉트와 시스템 방향을 기록한다.
- 명시적으로 결정되지 않은 내용은 `미결정 사항`에 분리한다.

## 1. 핵심 소재

### 1.1 배경

플레이어는 현대의 중소 SI업체에서 프로젝트를 관리한다.

외행성 개척, 범죄조직, 해결사 등의 우회적인 소재는 사용하지 않는다. 게임의 실제 시스템과 소재를 직접 일치시킨다.

### 1.2 플레이어 역할

플레이어는 한 프로젝트팀을 운영하는 PM 또는 그에 준하는 책임자다.

플레이어의 주요 업무는 다음과 같다.

1. 고객이 보낸 모호한 의뢰를 확인한다.
2. 필요한 작업과 확장 사양을 결정한다.
3. 예상 공수를 산정한다.
4. 각 작업에 적합한 근무자를 배치한다.
5. 자동 계산된 일정을 검토하고 필요할 때 조정한다.
6. 고객에게 계획을 제출한다.
7. 사양 변경, 정보 부족, 버그, 책임 공방에 대응한다.
8. 프로젝트를 검수 가능한 상태로 납품한다.

### 1.3 규모 원칙

프로젝트의 규모가 계속 커지는 성장 구조는 지향하지 않는다.

- 플레이어는 끝까지 하나의 팀을 관리할 수 있다.
- 회사 전체나 국가 규모의 조직을 운영하는 게임으로 확장하지 않는다.
- 초반과 후반 프로젝트의 물리적 규모는 비슷할 수 있다.
- 난도는 프로젝트 규모보다 불확실성과 복잡성으로 증가한다.

난도를 높이는 주요 요소는 다음과 같다.

- 모호한 요구
- 부족한 자료
- 상충하는 이해관계자
- 기존 시스템과의 연동
- 잦은 사양 변경
- 촉박한 일정
- 부족한 인력
- 담당자의 퇴사
- 인수인계 실패
- 숨겨진 예외 조건
- 고객 내부의 책임 회피
- 검수자와 요청자의 불일치

## 2. 핵심 게임 판타지

게임의 핵심 문장은 다음과 같다.

> 고객이 정확히 설명하지 못한 시스템을, 직원들이 퇴사하기 전에, 영업이 약속한 날짜까지 납품한다.

게임을 대표하는 상황은 다음 네 문장으로 요약한다.

> “안 돼요.”
>
> “그렇게 하면 버그 나요.”
>
> “제가 그렇게 하라고 했나요?”
>
> “아, 그리고 사양이 조금 바뀌었습니다.”

이 문장들은 단순한 직장 농담이 아니라 각각 다른 프로젝트 리스크를 나타낸다.

### 2.1 “안 돼요”

다음 상황을 포함한다.

- 필요한 정보가 전달되지 않았다.
- 고객의 요구가 서로 충돌한다.
- 기존 시스템이 해당 기능을 지원하지 않는다.
- 선행 작업이 완료되지 않았다.
- 담당자의 역량이 부족하다.
- 남은 일정 안에 완료할 수 없다.
- 접근 권한이나 테스트 환경이 없다.
- 담당자가 책임을 지기 싫어한다.
- 피로와 과로 때문에 정상적인 작업이 어렵다.

“안 돼요”는 작업을 거부하는 대사가 아니라 다음 의미에 가깝다.

> 현재 정보와 조건으로 진행하려면 무엇을 포기하거나 가정할지 결정해 달라.

### 2.2 “버그 나요”

다음 상황을 포함한다.

- 정상적인 사례만 전달받고 예외 사례를 받지 못했다.
- 실제 데이터가 샘플 데이터와 다르다.
- 기존 시스템이 문서와 다르게 작동한다.
- 고객 부서마다 같은 용어를 다르게 사용한다.
- 접근 권한이 없어 추측으로 개발했다.
- 테스트 환경과 운영 환경이 다르다.
- 급하게 확장 사양을 추가했다.
- 담당자가 바뀌면서 이전 가정이 전달되지 않았다.
- 피로한 근무자가 검증을 생략했다.

버그는 단순한 개발 실패가 아니라 다음 상황을 표현한다.

> 확인하지 않은 가정이 실제 환경과 충돌했다.

### 2.3 “제가 그렇게 하라고 했나요?”

다음 상황을 포함한다.

- 고객이 이전 발언을 부정한다.
- 영업 담당자가 약속한 내용을 기억하지 못한다.
- 구두 요청과 회의록이 다르다.
- 요청자와 검수자가 서로 다른 기준을 사용한다.
- 근무자가 지시를 다르게 이해했다.
- 고객의 여러 담당자가 상충하는 승인을 했다.
- 승인받지 않은 가정으로 작업을 진행했다.

회의록, 확인 메일, 승인 기록을 남기면 책임을 방어할 수 있다. 그러나 기록과 확인에도 일정과 공수가 필요하다.

### 2.4 직전 사양 변경과 추가 대응

고객은 프로젝트 도중 또는 검수 직전에 새로운 요구를 추가할 수 있다.

예:

> “관리자 버튼 하나만 추가하면 됩니다.”

실제로는 새로운 권한 체계, 데이터, 화면 흐름, 연동, 테스트, 보안 검토 또는 운영 절차가 필요할 수 있다.

플레이어는 변경 거절, 추가 비용 요구, 일정 연장, 기존 범위와 교환, 다른 작업 제거, 추가 인력 투입, 휴일 작업, 임시 대응 또는 다음 단계 이관 중 하나를 선택할 수 있다.

## 3. 의뢰 구조

### 3.1 고객은 완전한 정보를 제공하지 않는다

의뢰는 기본적으로 불완전한 상태로 도착한다.

예:

> “기존 주문 화면에 환불 기능을 추가해주세요. 다음 주까지요.”

초기 의뢰에 포함되지 않을 수 있는 정보:

- 전체 환불인지 부분 환불인지
- 배송 후에도 환불 가능한지
- 카드 외 결제수단이 있는지
- 포인트와 쿠폰을 어떻게 복원하는지
- 승인 권한이 누구에게 있는지
- 회계 시스템과 연동해야 하는지
- 테스트 계정이 있는지
- 운영 환경에 접근할 수 있는지
- 최종 검수자가 누구인지

### 3.2 모호함의 종류

#### 목적의 모호함

고객 자신도 원하는 결과를 정확하게 설명하지 못한다.

- “사용하기 편하게 해주세요.”
- “통합해주세요.”
- “요즘 것처럼 만들어주세요.”
- “AI를 넣어주세요.”
- “관리자 기능도 필요합니다.”
- “현황을 한눈에 보여주세요.”

#### 작업 정보의 부족

원하는 결과는 대략 알지만 작업에 필요한 자료가 없다.

- 기존 시스템 문서 없음
- 소스 접근 권한 없음
- 샘플 데이터 없음
- 실제 사용자 정보 없음
- 연동 규격 없음
- 테스트 계정 없음
- 업무 담당자 연락처 없음
- 검수 기준 없음
- 오류 재현 절차 없음

### 3.3 확인 행동

플레이어는 정보가 없는 상태에서 다음 행동을 선택할 수 있다.

- 고객에게 자료 요청
- 고객 통화
- 실무자 인터뷰
- 담당자 회의
- 기존 시스템 조사
- 샘플 데이터 요청
- 테스트 계정 요청
- 작은 시험 구현
- 가정을 세우고 우선 진행
- 가장 단순한 경우만 지원
- 위험을 기록하고 승인 요청
- 확인을 포기하고 일정 우선

확인하면 불확실성이 줄지만 일정이 소비된다. 확인하지 않으면 빠르게 진행할 수 있지만 검수와 운영에서 문제가 발생할 수 있다.

### 3.4 가정 기록

정보가 없는 상태에서 진행하려면 플레이어가 가정을 명시할 수 있다.

```text
환불 기능 작업 가정

- 전체 주문 취소만 지원
- 배송 시작 전 주문만 가능
- 카드 결제만 지원
- 관리자만 환불 가능
- 포인트와 쿠폰 복원은 제외
```

고객이 가정을 승인하면 이후 책임 공방에서 방어 자료로 사용할 수 있다. 승인받지 않았다면 고객은 “당연히 포함되는 줄 알았다”고 반응할 수 있다.

## 4. 근무자 능력 구조

근무자는 하나의 분야에 전문화되거나 두 개 이상의 분야를 다룰 수 있다.

현재 사용할 수 있는 작업 능력 명칭의 가안은 다음과 같다.

### 4.1 업무

시스템이 무엇을 어떻게 처리할지 이해하고 결정하는 능력이다.

- 업무 흐름
- 데이터 규칙
- 사용자 권한
- 승인 절차
- 예외 조건
- 고객 요구 해석
- 범위와 구조

### 4.2 화면

사용자가 시스템을 어떻게 보고 사용할지 결정하는 능력이다.

- 화면 구성
- 입력 흐름
- 오류와 알림 표현
- 보고서 형태
- 사용 편의성
- 시연 시 인상
- 관리자 대시보드

### 4.3 연동

결정된 내용을 실제 시스템에서 작동하게 만드는 능력이다.

- 기능 구현
- 기존 시스템 연결
- 데이터 이관
- 서버와 배포
- 보안
- 성능
- 장애 대응
- 외부 서비스 연동

### 4.4 근무자 유형 예시

```text
업무 7 / 화면 4 / 연동 2
고객 업무를 이해하고 구조를 정하는 데 강하다.

업무 4 / 화면 7 / 연동 3
사용자 접점과 화면 흐름에 강하다.

업무 2 / 화면 3 / 연동 7
구현과 장애 대응에 강하다.

업무 5 / 화면 5 / 연동 5
작은 기능을 혼자 완결할 수 있다.
```

능력 명칭 `업무 / 화면 / 연동`은 가안이며 최종 확정되지 않았다.

## 5. 유한한 작업 카탈로그

프로젝트마다 완전히 새로운 기능을 만들지 않는다. 유한한 기본 작업을 준비하고, 고객 의뢰는 기본 작업의 조합으로 구성한다.

업종은 기능이 아니라 표현상의 껍데기로 사용한다.

| 업종상의 표현 | 실제 작업 조합 |
|---|---|
| 병원 진료 신청 | 예약 + 승인 |
| 미용실 예약 | 예약 + 결제 |
| 회사 휴가 신청 | 신청 + 승인 |
| 장비 대여 | 예약 + 주문 |
| 공사 현장 일지 | 게시 + 사진 |
| 보험 사고 접수 | 신청 + 사진 |
| 식당 메뉴 주문 | 상품 + 주문 |
| 교육과정 신청 | 상품 + 예약 |
| 고객 문의센터 | 게시 + 알림 |
| 영업 현황판 | 기록 + 보고 |

### 5.1 기본 작업 후보

1. 회원과 권한
2. 게시와 기록
3. 신청과 승인
4. 예약과 배정
5. 상품과 주문
6. 결제와 환불
7. 파일과 사진
8. 알림과 소통
9. 조회와 보고
10. 관리자와 운영

초기 버전에서 모든 작업을 사용할지는 미정이다.

## 6. 기본 작업과 확장 사양

### 6.1 기본 원칙

각 작업은 다음으로 구성된다.

```text
기본형 작업
+ 확장 사양
+ 확장 사양
+ 확장 사양
```

기본형만 선택하면 싸고 빠르다. 확장 사양을 선택하면 기능 또는 품질이 향상되지만 다음 비용이 발생한다.

- 공수 증가
- 요구 능력 증가
- 일정 증가
- 새로운 선행 작업
- 추가 확인사항
- 테스트 범위 증가
- 버그 가능성 증가
- 운영 복잡도 증가
- 담당 가능한 근무자 감소

확장 사양은 작업당 우선 3개 정도만 제공한다.

### 6.2 옵션 선택 원칙

확장 사양은 붙이면 무조건 좋은 업그레이드가 아니다. 불필요한 확장 사양은 일정 낭비, 과도한 구현, 중요 작업 제외, 유지보수 부담, 테스트 증가, 버그 가능성 및 근무자 과로를 만든다.

반대로 필요한 확장 사양을 빼면 실제 운영에서 장애가 발생하거나 검수에 실패할 수 있다.

### 6.3 초기 작업별 확장 사양 예시

| 기본 작업 | 확장 사양 1 | 확장 사양 2 | 확장 사양 3 |
|---|---|---|---|
| 회원과 권한 | 소셜 로그인 | 다중 권한 | 2단계 인증 |
| 게시와 기록 | 댓글 | 비밀글 | 대규모 조회 |
| 신청과 승인 | 다단계 결재 | 대리결재 | 변경 이력 |
| 예약과 배정 | 반복 예약 | 대기자 | 동시예약 방지 |
| 상품과 주문 | 상품 옵션 | 부분 취소 | 지점별 가격 |
| 결제와 환불 | 부분 환불 | 복합 결제 | 중복 결제 방지 |
| 파일과 사진 | 썸네일 생성 | 위변조 확인 | 대규모 동시 업로드 |
| 알림과 소통 | 다채널 발송 | 예약 발송 | 실패 재처리 |
| 조회와 보고 | 실시간 집계 | 엑셀 출력 | 대용량 대응 |
| 관리자와 운영 | 일괄 처리 | 감사 로그 | 되돌리기 |

이 표의 구체적인 작업과 확장 사양은 초기 후보이며 최종 확정되지 않았다.

### 6.4 파일과 사진 예시

```text
기본 사양
- JPG·PNG 업로드
- 한 건당 최대 5장
- 원본 저장
- 관리자 다운로드
기본 공수: 4인일

+ 썸네일 자동 생성
추가 공수: 2인일

+ 위변조 확인
추가 공수: 4인일

+ 대규모 동시 업로드
추가 공수: 5인일
```

### 6.5 확장 사양 간 충돌

일부 확장 사양은 서로 충돌하거나 추가 구조를 요구할 수 있다.

예를 들어 `위변조 확인`은 원본 보존을 요구하지만 `썸네일 생성`, `자동 회전`, `크기 축소`는 이미지를 변환한다. 따라서 원본 별도 보존, 표시용 변환본 생성, 원본 해시 기록 및 변환 이력 기록이 필요할 수 있다.

옵션 간 충돌을 시스템으로 어디까지 표현할지는 미정이다.

## 7. 원형 작업 구성 인터페이스

### 7.1 기본 형태

계획 화면은 하나의 원으로 구성한다.

- 원은 현재 의뢰에서 선택 가능한 작업 종류 수만큼 분할한다.
- 하나의 원 조각은 하나의 기본 작업이다.
- 각 조각은 `ON/OFF`할 수 있다.
- `ON`이면 프로젝트 범위에 해당 작업을 포함한다.
- `OFF`이면 프로젝트 범위에서 해당 작업을 제거한다.

### 7.2 확장 사양 표시

각 작업 조각의 바깥 가장자리에 확장 사양을 표시한다.

- 확장 사양마다 체크박스가 있다.
- 체크박스로 확장 사양을 켜거나 끈다.
- 확장 사양 명칭을 누르면 상세정보를 연다.
- 작업이 `OFF`이면 해당 작업의 확장 사양은 선택할 수 없다.
- 작업을 `OFF`로 바꾸면 선택된 확장 사양도 해제한다.

확장 사양의 화면 명칭은 짧게 표시한다.

```text
□ 썸네일
□ 위변조
□ 동시접속
```

### 7.3 작업 조각 상태

#### OFF

- 회색 표시
- 공수 계산에서 제외
- 확장 사양 선택 불가
- 담당자 없음
- 일정 없음

#### ON, 미배정

- 기본 작업 공수 반영
- 확장 사양 선택 가능
- 담당자 미지정 경고

#### ON, 배정 완료

- 담당자 표시
- 예상 시작일과 완료일 표시
- 필요 능력과 담당자 적합도 표시

#### 위험 상태

- 담당자의 능력 부족
- 마감 초과
- 선행 작업 미완료
- 고객 정보 부족
- 테스트 환경 없음
- 과도한 확장 사양
- 담당자 과부하
- 확장 사양 간 충돌

### 7.4 조각 내부 표시 정보

```text
사진
ON

기본 4인일
확장 +6인일

담당: 배리나
4/1~4/10
```

### 7.5 원 중앙 표시 정보

```text
전국 대리점 사진 접수

선택 작업: 4/6
선택 확장: 5/12
총공수: 31인일

예상 완료: 4월 18일
고객 마감: 4월 16일

2일 초과
```

작업 또는 확장 사양을 토글하면 선택 작업 수, 선택 확장 수, 총공수, 요구 능력, 담당자 부족, 예상 완료일, 마감 초과 및 주요 위험을 즉시 다시 계산한다.

### 7.6 상세정보 패널

작업 또는 확장 사양 이름을 누르면 별도의 상세 패널을 연다.

```text
위변조 확인

업로드된 원본의 해시값과 수신 시각을 보존합니다.
사진이 이후 수정되지 않았음을 확인할 수 있습니다.

추가 공수: 4인일
주요 능력: 업무 4 / 연동 7

필요 정보:
- 원본 보존기간
- 요구되는 증빙 수준
- 이미지 변환 허용 여부

새로운 위험:
- 자동 축소·회전과 충돌 가능
- 저장공간 증가
- 원본과 변환본 관리 필요
```

## 8. 공수 산정

### 8.1 공수와 일정의 분리

작업과 확장 사양을 선택하면 먼저 공수를 산정한다. 공수는 작업을 완료하는 데 필요한 총노동량이다.

```text
사진 등록 기본형       4인일
+ 썸네일 자동 생성     2인일
+ 위변조 확인          4인일
----------------------------
총공수                 10인일
```

공수는 담당자가 지정되기 전에도 계산할 수 있다.

### 8.2 담당자에 따른 실제 기간

담당자를 지정하면 담당자의 능력, 작업 적합도, 일일 산출, 피로, 성격과 퍽, 기존 일정, 휴식일, 선행 작업 및 인수인계 비용으로 실제 작업기간을 계산한다.

```text
배리나 배치

적합도: 높음
일일 예상 산출: 1.25인일
총공수: 10인일
예상 작업기간: 8근무일
```

역량이 낮은 담당자를 배치하면 작업기간, 실패 확률, 버그 확률, 추가 피로와 불만이 증가한다.

## 9. 사람과 일정 배치

### 9.1 담당자 지정

작업이 결정되고 공수가 산정되면 각 작업에 근무자를 지정한다. 근무자는 특정 분야 전문형, 두 분야 복합형 또는 세 분야 범용형일 수 있다.

한 작업에 한 명의 주 담당자를 둘지 여러 명을 배치할지는 최종 확정되지 않았다.

### 9.2 자동 일정

담당자를 지정하면 일정은 기본적으로 자동 계산한다.

자동 계산 시 다음을 고려한다.

- 작업 공수
- 담당자의 일일 산출
- 담당자의 기존 일정
- 주말과 휴식일
- 휴가와 건강 상태
- 선행 작업
- 고객 검토일
- 프로젝트 마감
- 병행 가능 여부
- 인수인계 비용

### 9.3 플레이어의 일정 개입

일정은 기본 자동 계산이지만 플레이어가 필요할 때 시작일 고정, 우선순위 변경, 담당자 교체, 작업 보류, 병행 작업 허용, 휴일 작업 요청, 일정 연장 협상, 작업 제거 또는 확장 사양 제거로 개입할 수 있다.

구체적인 수동 일정 기능 범위는 미정이다.

## 10. 계획 제출과 고객 검토

1. 의뢰 메일을 연다.
2. 의뢰 내용과 제공 자료를 확인한다.
3. 필요하면 통화·인터뷰·회의를 요청한다.
4. `계획하기`를 선택한다.
5. 원형 작업판에서 기본 작업을 `ON/OFF`한다.
6. 각 작업의 확장 사양을 선택한다.
7. 총공수와 정보 부족 경고를 확인한다.
8. 각 작업에 담당자를 지정한다.
9. 자동 계산된 일정을 확인한다.
10. 과부하, 선행관계, 마감 초과를 조정한다.
11. 고객에게 계획을 제출한다.
12. 고객 검토 중에는 계획을 수정할 수 없다.
13. 고객이 승인하거나 반려한다.
14. 반려되면 고객 의견과 함께 계획판을 다시 연다.
15. 승인되면 실행 일정으로 전환한다.

## 11. 퇴사와 채용

기존의 재생 시스템은 현대 SI 소재에서 `퇴사와 채용`으로 변경한다.

| 기존 개념 | SI 소재의 해석 |
|---|---|
| 재생 | 기존 직원 퇴사 후 후임 채용 |
| 기본 비용 | 채용비와 공석 대응비 |
| 능력 계승 | 경력직 또는 유사 전문인력 채용 |
| 퍽 계승 | 인수인계, 문서화, 동행 근무 |
| 성격 재추첨 | 새 직원의 성격과 업무 태도 |
| 경험 초기화 | 회사와 고객에 대한 맥락 부족 |
| 급여 초기화 | 신입 또는 낮은 연차의 초기 급여 |
| 피로 초기화 | 새 직원이 과로가 없는 상태로 합류 |
| 담당 업무 유지 | 후임자가 기존 자리와 업무를 인계 |

### 11.1 저비용 채용

- 신입 채용
- 낮은 초기 급여
- 낮거나 초기화된 능력
- 고객과 프로젝트 맥락 부족
- 높은 인수인계 비용

### 11.2 능력 보존

추가 비용을 지불해 경력직을 채용한다.

- 기존 직원과 유사한 능력
- 더 높은 채용비
- 더 높은 급여 가능성
- 전문 작업의 연속성 확보

### 11.3 노하우 보존

추가 비용과 시간을 사용해 인수인계를 진행한다.

- 문서화
- 고객 연락처와 관계 전달
- 장애 대응 기록
- 프로젝트 가정 전달
- 실무 노하우 보존
- 일부 퍽 또는 특성 계승

### 11.4 퇴사 전조 후보

- 메신저 답변이 짧아짐
- 추가 대응 거부
- 휴식 요청 증가
- 급여 면담 요청
- 프로젝트 변경 요청
- 업무 문서화 시작
- 동료에게 업무를 넘김
- 고객 앞에서 회사 방침 비판
- 반복적인 과로
- 신뢰 또는 만족도 하락

퇴사와 채용의 구체적인 발생 규칙은 미정이다.

## 12. 아트와 콘텐츠 범위

현대 SI 소재는 별도의 결과물 아트를 대량으로 요구하지 않는다.

주요 화면은 업무용 데스크톱 형태로 구성할 수 있다.

- 메일
- 메신저
- 요구사항 목록
- 원형 작업 계획판
- 간트 차트
- 회의록
- 가정 기록
- 화면 구성도
- 장애 보고서
- 테스트 결과
- 고객 검수 의견
- 직원 프로필
- 프로젝트 회고

프로젝트마다 실제 서비스를 완성된 UI로 그릴 필요는 없다. 결과는 고객과 근무자의 보고, 검수 의견, 장애 기록과 프로젝트 회고로 전달한다.

## 13. 현재 결정된 사항

- 소재는 현대 SI업체다.
- 플레이어는 PM 또는 프로젝트 책임자다.
- 프로젝트 규모가 계속 커지는 성장 구조는 사용하지 않는다.
- 고객은 모호하거나 정보가 부족한 의뢰를 보낸다.
- 정보 확인에는 시간이 소비된다.
- 확인하지 않고 가정을 세워 진행할 수 있다.
- 사양 변경과 추가 대응이 핵심 사건이다.
- 버그는 정보 부족과 잘못된 가정에서도 발생한다.
- 책임 공방과 기록 관리가 중요하다.
- 기능 종류는 무한히 만들지 않는다.
- 유한한 기본 작업을 조합해 프로젝트를 구성한다.
- 각 작업에는 기본형이 있다.
- 각 작업에는 우선 약 3개의 확장 사양을 둔다.
- 확장 사양은 공수와 위험을 증가시킨다.
- 확장 사양은 필요한 것만 선택해야 한다.
- 계획 인터페이스는 원형이다.
- 원은 선택 가능한 작업 수만큼 분할된다.
- 조각 하나는 작업 하나다.
- 작업은 `ON/OFF`로 추가하거나 제거한다.
- 확장 사양은 작업 조각 가장자리에 표시한다.
- 확장 사양은 체크박스로 토글한다.
- 확장 사양 이름을 누르면 상세정보를 연다.
- 작업과 확장 사양이 결정되면 공수를 산정한다.
- 공수가 산정된 뒤 사람과 일정을 지정한다.
- 일정은 기본적으로 자동 계산한다.
- 기존의 재생은 퇴사와 채용으로 변경한다.

## 14. 미결정 사항

- 게임의 제목
- 회사와 팀의 정확한 명칭
- `업무 / 화면 / 연동` 능력 명칭
- 초기 기본 작업의 정확한 종류와 개수
- 각 작업의 확장 사양 최종 목록
- 원형 계획판에서 허용할 최대 작업 조각 수
- 한 작업에 한 명만 배치할지 여러 명을 배치할지
- 수동 일정 조정의 범위
- 확장 사양 간 충돌을 어느 수준까지 표현할지
- 고객 명확도와 환경 파악도를 별도 수치로 둘지
- 고객의 숨은 중요도 계산 방식
- 불필요한 과잉 사양의 구체적인 불이익
- 버그 발생과 발견 방식
- 검수와 운영 장애의 관계
- 퇴사 발생 규칙
- 채용 후보 생성 방식
- 인수인계로 보존되는 능력과 퍽의 범위
- 운영자금과 프로젝트 보상 구조
- 게임 종료 조건과 최종 점수
- 기존 `60/30/10` 슬롯을 완전히 제거할지 여부

## 15. 한 문장 요약

> 유한한 기본 작업과 확장 사양을 조합하고, 부족한 정보 속에서 공수·인력·일정을 결정해 고객 검수까지 버티는 SI 프로젝트 관리 시뮬레이션.
